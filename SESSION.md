## 2026-11-04 — конкретные причины доказанной невозможности

### Что сделано

- Новый модуль `backend/app/diagnosis.py`. При `INFEASIBLE` расчёт называет
  конфликтующие условия: смены, сотрудников и само условие. Закрыт разрыв из
  предыдущей записи и требование `docs/PRODUCT_PLAN.md:134`.
- `backend/app/solver.py`: режим `probe` у `solve()` отвечает только на вопрос
  «есть ли проверенное расписание для именно этих входов» (та же модель, тот же
  валидатор, без цели, без вопроса про неизвестное и без объяснения). Им теперь
  пользуется и `no_clarification_can_help`. Вынесен общий `run()`, основной поиск
  идёт с прежними настройками.
- `SolveIssue.conditions` (`kind`, `shiftId`, `employeeId`, `role`, `removalCheck`),
  код `conflict`. Коды `pinned_absence`, `fixed_absence`, `fixed_pin_conflict`
  сохранены. Типы API перегенерированы.
- `RunReport` не менялся: сообщение разбито на строки, в `workspace.css` одна
  строка `white-space: pre-line`.

### Как устроено

Условия семи видов: закрепление исходника, закрепление условий, отсутствие на
смене, нет роли, недоступность, лимит часов, требование закрыть смену. Правила «один
человек на смене» и «без пересечений» не снимаются.

1. Отдельная модель с `add_assumptions` предлагает конфликт
   (`sufficient_assumptions_for_infeasibility`). Ей не доверяем.
2. Условия снимаются из настоящих входов (`without`), вопрос задаётся обычному
   `solve(probe=True)`. Подтверждается, что конфликт настоящий, лишнее убирается.
3. Если без конфликта решения всё равно нет, ищется следующий. Конфликты не
   пересекаются, цикл заканчивается, когда без всех них решение есть.
4. Для каждого условия проверяется, что будет без него: сначала только на
   подтверждённой доступности, затем с допущением про неизвестное.

### Ключевые решения

- Предложения от литералов не считаются доказательством. Если в отдельной модели
  ошибка, проверка отклонит конфликт и останется общий ответ, а не выдуманная причина.
  Этому есть тест с подставленным ложным конфликтом.
- `without` меняет именно входы: каждое снятие является правкой, которую может
  сделать человек, поэтому сверка в тесте пишется независимо. Смена без покрытия
  убирается из входов, а если на неё ссылается оставшееся условие, её берёт
  сотрудник-заглушка (ID начинается с NUL, в PostgreSQL такого быть не может).
- Требование закрыть смену считается условием, а не жёстким правилом. Иначе не
  называется случай «пересекающихся смен больше, чем людей», а отчёт не может
  указать смену в конфликтах из ролей. Это снятие только в проверке: результат
  расчёта ничего не ослабляет.
- Условие, снятие которого не помогает, отчёт называет прямо (`no_solution`), а не
  прячет. Пример на экране: Илья закреплён на `s04` без роли. Выдать ему роль
  бесполезно, потому что `s03` доступна только ему и пересекается с `s04`, поможет
  только снятие закрепления.
- Диагностика выдаёт всё или ничего. Частичный отчёт невозможен: без поиска
  остальных конфликтов нельзя проверить снятие условия.
- `cp_model_probing_level=0` только вне основного поиска: вдвое дешевле на 50×100,
  симметрия оставлена, чтобы не замедлять доказательства «голубятни».
- Быстрый путь: сначала расписание, где смены вне конфликта остаются как в уже
  найденном. Успех засчитывается (более строгая задача, тот же валидатор), неудача
  ничего не доказывает и ведёт к полному поиску. «Некому взять» на 50×100: 9,75 с → 3,4 с.
