# Этап 3 — расчёт и независимая проверка

Реализовано 2 ноября 2026 года. Это локальный контур разработки на синтетических данных. Существующие лендинг, палитра, типографика, графика и трёхпанельная структура сохранены.

## Рабочий цикл

1. Импортировать CSV/XLSX либо открыть сохранённый проект.
2. Задать отсутствие сотрудника и сохранить условия. Текст задачи пока служит описанием; он не преобразуется автоматически в правила.
3. Нажать «Рассчитать сохранённые условия». API сначала сохраняет Run в PostgreSQL и возвращает его ID.
4. Отдельный Python-процесс забирает задание из очереди и строит назначения через OR-Tools CP-SAT.
5. Независимый модуль без зависимости от CP-SAT заново проверяет назначения и считает метрики.
6. Интерфейс показывает различные проверенные варианты, их последствия, журнал и ссылки на исходные ячейки.
7. Выбранные назначения можно закрепить: атомарно создаются новая версия условий и новый запуск. Остальное расписание рассчитывается заново.

Новый Run привязан к SourceVersion, её hash, TaskSpec, версии движка и параметрам поиска. Старый ответ не меняет текущие версии проекта. UI принимает ответ только для совпадающих project/source/task; запоздалый опрос не переводит завершённый Run обратно в выполнение.

## Поддержанные условия

- Ровно один сотрудник на каждую импортированную смену. Сами интервалы и потребность в покрытии остаются заданными исходником.
- Только роль из списка ролей сотрудника.
- Только подтверждённая доступность. Неизвестные значения исключены из допустимых назначений.
- Отсутствие действует на весь временной интервал выбранных смен, включая пересекающиеся с ним смены.
- Один человек не может работать на пересекающихся интервалах. Соприкасающиеся границы разрешены.
- Закрепления исходника сохраняются; дополнительные закрепления берутся из конкретной версии условий.
- Индивидуальные максимальные недельные минуты не превышаются.

Время считается по UTC-интервалам в целых минутах; явные смещения учитывают переходы часового пояса. Проверяются введённые правила. Соответствие всем трудовым нормам не заявляется; перерывы, минимальный отдых и правила доплат в контракт пока не входят.

## Приоритеты и суммы

Первый приоритет — минимум изменённых назначений. При известных ставках среди доказанно лучших по этому приоритету решений дополнительно минимизируется оплата.

Второй приоритет — минимум оплаты по известным почасовым ставкам. При доказанном минимуме оплаты дополнительно уменьшается количество перестановок. Если назначения совпали, второй экземпляр не выдаётся; факт совпадения остаётся в журнале. Искусственно отличающийся третий вариант не создаётся.

Приоритет оплаты доступен только при известных ставках всех сотрудников. Нулевая ставка известна; пустая ставка неизвестна. Неизвестная ставка в выбранных назначениях даёт часы и перестановки, но не выдуманную денежную сумму.

Оплата каждого назначения: `(минуты × ставка_в_минимальных_единицах + 30) // 60`. Округление до минимальной денежной единицы, половина вверх, отдельно по назначению. Затем складываются назначения; разница считается между округлёнными суммами. Налоги и доплаты не моделируются. Валюта и период берутся из исходника.

Метрики включают изменения, затронутых сотрудников, покрытие, общие минуты, минуты по каждому человеку, исходную и итоговую оплату, разницу и список неизвестных ставок.

## Честные статусы

Состояние выполнения, поиск и независимая проверка разделены:

- Run: `queued`, `running`, `completed`, `needs_clarification`, `failed`, `cancelled`.
- Каждая попытка CP-SAT: `OPTIMAL`, `FEASIBLE`, `INFEASIBLE`, `MODEL_INVALID`, `UNKNOWN`.
- Проверка назначения: `pass`, `unknown`, `fail`.

`OPTIMAL` относится к главному приоритету и модели с подтверждённой доступностью. Статус дополнительной оптимизации записан отдельно. `FEASIBLE` позволяет выдать проверенный допустимый вариант, не объявляя оптимальность. `UNKNOWN` без результата даёт исчерпанный лимит; это не доказанная невозможность.

Если при подтверждённой доступности решения нет, а потенциальные кандидаты имеют неизвестную доступность, выполняется ещё один поиск: вся неизвестная доступность считается подтверждённой. Такой поиск ничего не публикует, его результат виден только в журнале расчёта. Если решение появляется или лимит исчерпан, Run требует уточнения. Если решения нет и так, невозможность доказана при любых значениях неизвестной доступности, и уточнение не предлагается. Если прямо противоречат друг другу отсутствие и закрепление (исходника или условий) либо два закрепления одной смены, это конкретный доказанный конфликт, и дополнительный поиск не нужен.

Отдельный валидатор проверяет версии/ID, покрытие, доступность, роли, закрепления, часы и пересечения. При нарушении или неизвестной доступности рассчитанный вариант не выдаётся.

Определения статусов и целочисленная модель основаны на [официальной документации CP-SAT](https://developers.google.com/optimization/cp/cp_solver). Применение ограничений к сотрудникам показано в [официальном примере расписаний](https://developers.google.com/optimization/scheduling/employee_scheduling); правила WUJI заданы приведённым выше контрактом и проверяются собственными тестами.

### Причины невозможности

Когда невозможность доказана, расчёт отдельно называет конфликтующие условия: смены, сотрудников и само условие. Условия семи видов: закрепление исходника, закрепление условий, отсутствие на смене, отсутствие роли у сотрудника, недоступность на смене, лимит часов и требование закрыть смену. Правила «один человек на смене» и «нельзя работать на пересекающихся сменах» не снимаются, а пересечение смен конфликта названо как факт из исходника.

Диагностика идёт рядом с расчётом и ничего не публикует. Основная модель предположений не получает, поэтому назначения не смещаются. Отдельная модель с литералами CP-SAT (`add_assumptions`, `sufficient_assumptions_for_infeasibility`) только предлагает кандидата. Каждое утверждение решается обычным поиском на основной модели с настоящим снятием условия из входов, а найденное расписание проходит независимый валидатор:

1. Условия конфликта сами по себе не имеют решения. Иначе предложение отбрасывается.
2. Лишние условия убираются по одному, пока без любого из оставшихся конфликт не исчезает. Первыми уходят факты о сотрудниках, последними закрепления, поэтому в отчёте остаётся то, что задал человек.
3. Для каждого условия отдельно проверяется, что будет без него. Результат записан в `SolveIssue.conditions[].removalCheck`: `solution` — проверенное расписание есть; `solution_if_confirmed` — появляется, только если подтвердится неизвестная доступность; `no_solution` — решения нет и так, и отчёт говорит об этом прямо.

Если конфликтов несколько, снятие одного условия не может дать решения. Такие конфликты не пересекаются по условиям, каждый из них проверяется при снятых остальных, и сообщение об этом предупреждает. Если ни одно условие конфликта по отдельности не помогает, отчёт добавляет, что будет без всех условий вместе. Снятие условий здесь только проверка: обязательные условия в расчёте не ослабляются.

Диагностика укладывается в общий лимит запуска. Если времени не хватило или поиски разошлись, остаётся общий ответ «Минимальный набор причин не определялся», а причина видна в журнале. Коды `pinned_absence`, `fixed_absence`, `fixed_pin_conflict` сохранены для соответствующих конфликтов, остальные получают код `conflict`. Общий ответ сохраняет код `infeasible`. Запись в журнале есть всегда, поисков диагностики в `attempts` нет.

Цена: 0,03–0,08 с на примере 10×14. На потолке 50×100 при лимите 10 с простой конфликт занимает 0,5–1,2 с, смена, которую некому взять (51 условие), — 3,4 с. Пять таких смен сразу в 10 с не укладываются и получают общий ответ.

## Очередь, отмена и восстановление

`npm run api` запускает API и отдельный worker из одного backend-кода. API не выполняет CP-SAT внутри HTTP-запроса.

Очередь находится в PostgreSQL. Worker забирает строку через `FOR UPDATE SKIP LOCKED`, записывает token и heartbeat. На одну комбинацию project/source/task допускается один активный запуск; для новой версии условий можно поставить новое задание, пока историческое ещё выполняется.

Лимит поиска — 10 секунд из UI; API принимает целые значения 1–30. На Run используется один поток CP-SAT и seed 0. Лимит распределяется между приоритетами; время поиска, статусы попыток и наблюдаемые события сохранены в результате.

Отмена очереди немедленна. При выполнении heartbeat-поток замечает запрос отмены и вызывает `stop_search`. Перед записью результата worker под блокировкой повторно проверяет token, состояние и отмену. Поэтому отмена, пришедшая между окончанием поиска и записью, не публикует вариант.

При чтении состояния через API или следующем обходе worker запуск без heartbeat за 30 секунд помечается ошибкой с явным событием; его можно повторить новым Run. Старый worker не вправе заменить терминальный результат. Очередь и завершённые результаты сохраняются после перезапуска.

PostgreSQL-триггер запрещает изменение входов Run, удаление запусков и любые изменения завершённых строк. Повтор запроса с тем же ключом возвращает тот же Run; ключ для других входов приводит к конфликту.

## Частичное закрепление

`TaskSpec.fixedAssignments` хранит явные назначения. «Сохранить закрепления и пересчитать» берёт только назначения прошедшего проверку сценария текущих версий. Создание новой TaskSpec и постановка нового Run выполняются одной транзакцией.

Выбранные назначения не объединяются с остальными без проверки. Новый CP-SAT-расчёт учитывает закрепления и заново проверяется. В центральной области закрепления можно снять и сохранить новую версию условий. В интерфейсе изменение текста или отсутствия сохраняет действующие закрепления до их явного снятия.

## API

Все пути начинаются с `/api/v1/projects/{projectId}`.

| Действие | Маршрут |
| --- | --- |
| Создать запуск | `POST /runs` |
| История, с фильтрами source_id / task_id | `GET /runs` |
| Состояние, события и результат | `GET /runs/{runId}` |
| Отменить | `POST /runs/{runId}/cancel` |
| Закрепить выбранные смены и пересчитать | `POST /runs/{runId}/fix` |

`POST /runs`: sourceVersionId, taskSpecId, requestKey и необязательный maxTimeSeconds. Закрепление дополнительно передаёт scenarioId и shiftIds. История возвращает до 100 последних запусков выбранных входов. Доступ к Run другого projectId возвращает 404; это проверка принадлежности, а не аутентификация.

OpenAPI и TypeScript-типы генерируются командой `npm run api:types`; `api:types:check` обнаруживает расхождение.

## Проверенные сценарии

- На завершении этапа 3: 64 backend-теста и 25 тестов TypeScript/HTTP-клиента. Актуальные проверки следующей итерации описаны в [INTENT_STAGE.md](./INTENT_STAGE.md).
- Для маленькой задачи результаты обоих приоритетов сопоставлены с полным перебором допустимых назначений и ручными суммами.
- Проверены несовместимое закрепление, неизвестная доступность, неизвестная и нулевая ставка, отсутствие необходимости перестановок, равные варианты, таймаут, отмена, ручное повреждение назначений, смещение времени, округление и новые закрепления.
- Названные причины сверяются полным перебором назначений без CP-SAT и кода диагностики: судья — только валидатор, снятие условий написано в тесте отдельно. Проверяется, что конфликт настоящий, что ни одно условие в нём не лишнее, что вердикт каждого условия верен и что без всех конфликтов решение есть.
- API-тесты проверяют настоящие миграции PostgreSQL, очередь, повтор, конкурентный старт, неизменяемость, потерю worker, старые входы, перезапуск приложения и отмену непосредственно перед записью найденного решения.
- В браузере проверены расчёт, история, отмена, закрепление с перерасчётом, сохранение/снятие закреплений и мобильный цикл 390×844.

В основном синтетическом проекте «Пример · Студия Север» сохранены SourceVersion V3 и условия V6–V9. V9 задаёт отсутствие Анны на интервале s05 и сохраняет исходные закрепления. Первый вариант: одна замена на Софию, 31 680 ₽ за неделю, разница 0 ₽. Второй: Анна → Денис на s05 и Денис → Олег на s08, 31 040 ₽, разница −640 ₽. Оба дают 112 часов и покрытие 14/14. V7/V8 сохраняют закрепление Дениса на s05 и проверенный перерасчёт остальных смен. V6 также содержит отменённый запуск.

Дополнительные синтетические проекты: «Проверка · закрепление и отсутствие», «Проверка · неизвестная доступность», «Проверка · неизвестная ставка». Снимки: [calculation-preview/](./calculation-preview/).

## Граница готовности

На следующей итерации реализован [черновик условий из текста](./INTENT_STAGE.md) с обязательным подтверждением; успешный живой ответ провайдера ещё не проверен. Текст не применяется автоматически. Приоритет теперь сохраняется в TaskSpec; расчёты получили версию schedule-cpsat/2, исторические результаты сохраняют свои метаданные. Затем реализованы [ручные версии, повторная проверка, утверждение и выдача результата](./APPROVAL_STAGE.md). Ручная версия не наследует оптимальность исходного расчёта. В schedule-cpsat/3 условия без решения при любых значениях неизвестной доступности стали завершаться доказанной невозможностью, а не просьбой уточнить; если решение есть, назначения те же. Текущая версия — schedule-cpsat/4: варианты, outcome и статус запуска те же, а при доказанной невозможности отчёт называет проверенные конфликтующие условия. Сохранённые запуски остаются со своей версией. Доступ нескольких пользователей остаётся будущей работой. Экспорт сохранённого исходника продолжает работать отдельно. Рабочие данные во внешние системы не записываются.
