## Статус реализации на 2 ноября 2026 года

Первая итерация (этапы 0–1 на синтетических данных) реализована: `/workspace`, три связанные области, регулируемые разделители, пять ситуаций, варианты, метрики, источники и проверки примера. Сохранены визуальные эталоны, входной контракт и CSV/JSON-примеры. Подробности и ограничения: [WORKSPACE_DEMO.md](./WORKSPACE_DEMO.md).

Вторая итерация (этап 2) реализована: локальный FastAPI/PostgreSQL, миграции, CSV/XLSX-предпросмотр и подтверждение, оригиналы и hash, неизменяемые версии исходника и условий, история, экспорт и повторный импорт. TypeScript-контракт генерируется из backend/OpenAPI. Подробности: [DATA_STAGE.md](./DATA_STAGE.md).

Третья итерация (этап 3) реализована: OR-Tools CP-SAT, независимый серверный валидатор, метрики и Evidence, постоянная очередь отдельного worker, отмена, повтор, история и обнаружение потерянных запусков. Частичное закрепление создаёт новые условия и новый расчёт. Подробности: [CALCULATION_STAGE.md](./CALCULATION_STAGE.md).

Четвёртая итерация (этап 4) реализована и проверена без живого API: один адаптер OpenAI, строгая схема цитат, серверное сопоставление с исходником, вопросы, четыре группы подтверждения, новая версия TaskSpec, очередь, отмена, usage и оценка стоимости. Контрольный браузерный режим явно обозначен. Первоначальный живой запрос получил отказ авторизации; успешное подключение и качество реальной модели остаются непроверенными по решению владельца продолжить без API. Подробности: [INTENT_STAGE.md](./INTENT_STAGE.md).

Пятая итерация реализовала локальную часть этапа 5: ручные версии с повторной проверкой, неизменяемое утверждение точных входов и назначений, CSV/XLSX из утверждённого снимка, квитанции и безопасные повторы. Экспорт повторно читается с отсутствием и дополнительными закреплениями. Добавлены npm run check и GitHub Actions workflow; удалённый CI ещё не запускался. Подробности: [APPROVAL_STAGE.md](./APPROVAL_STAGE.md).

Реальный обезличенный пример и проверка контракта пилота остаются открытыми. Следующая работа перед общим пилотом — аутентификация, изоляция рабочих областей и проверка на реальном эпизоде. Успешный живой цикл модели также ещё не подтверждён.

## 1. От чего начинаем

Исходное состояние перед первой итерацией:

- React 19, Vite, TypeScript, Tailwind CSS, React Router; GSAP и Lenis уже подключены.
- Единственный маршрут `/` показывает лендинг: выбор OS, hero, карточки, терминал, статистика, footer.
- В `src/` нет рабочего пространства, импорта пользовательских файлов, серверного API, сохранения проектов и расчётного движка.
- В `package.json` пока только `dev`, `build`, `preview`; автоматические предметные и браузерные проверки предстоит добавить вместе с соответствующим поведением.
- `npm run build` успешно выполнен 1 ноября 2026 года. Лендинг открыт локально и визуально проверен.
- Исходная ревизия отслеживаемого приложения: `8cc4ec5`. Продуктовый план находится в ещё не отслеживаемом Git каталоге `docs/`; существующее изменение `.claude-docs/session-activity.md` не относится к реализации.

Первый предметный сценарий берём из продуктового плана: **исправление недельного расписания сотрудников после отсутствия человека**. Он проверяет общий цикл WUJI: исходник → условия → варианты → последствия → проверка → утверждение → экспорт.

## 2. Дизайн — обязательный контракт

### Визуальный эталон

Источник визуальных решений — существующий сайт и его исходники:

| Элемент | Что сохраняем | Где уже определено |
| --- | --- | --- |
| Палитра | Чёрный `#000000`, светлый `#FFFFFF` / `#E8E8E8`, сетка `#1A1A1A`, поверхность `#0A0A0A` | `src/index.css`, `tailwind.config.js`, компоненты |
| Акценты | Зелёный `#00FF41`, красный `#FF3333`, оранжевый `#FF8C00` | Navigation, OSSelectorSection, TerminalPreviewSection |
| Типографика | DotGothic16 для выразительных заголовков, VT323 для основного терминального текста, Space Mono для данных и подписей | `index.html`, `src/index.css` |
| Геометрия | Прямые углы, тонкие линии, чёткая сетка, контурные кнопки и плашки | `src/components/SkillCard.tsx` и секции лендинга |
| Графика | Логотип WU JI / 無極, голова, мозг, пиксельный курсор | `public/images/` |
| Эффекты | CRT-развёртка, свечение, цифровой дождь, набор текста, существующий характер переходов | ScanlineOverlay, ProgressiveCodeCanvas, Typewriter, GSAP |
| Голос интерфейса | Короткие подписи, `//`, квадратные скобки, терминальные акценты; понятный текст действий | Navigation, SectionLabel, TerminalPreviewSection |

Рабочее пространство продолжает этот визуальный язык. Его таблицы и формы получают рабочую плотность и читаемые размеры, сохраняя существующие шрифты, цвета, графику и геометрию. Анимации лендинга сохраняются; в таблицах, вводе и журнале эффекты не мешают чтению, выделению и управлению.

Правила реализации:

1. Сохраняем `/` и порядок его секций. Добавляем продукт на `/workspace`; вход с лендинга оформляем существующим стилем ссылки/кнопки.
2. Используем текущие классы и значения. Дополнительные стили ограничиваем рабочим пространством; массовая замена глобальных стилей в эту работу не входит.
3. У общих компонентов переиспользуем внешний вид, отделяя его от поведения лендинга: рабочей странице нужны свои действия, прокрутка и состояние. Lenis остаётся в Home; панели имеют независимую прокрутку.
4. Сохраняем изображение логотипа и его пиксельный характер. Декоративный мозг используем там, где он не закрывает содержимое.
5. Для новых состояний используем существующую палитру и текстовые обозначения. Цвет бренда сам по себе не означает ошибку, допуск или завершённую проверку.
6. Проверяем кириллицу, числа, даты, длинные имена и контраст. Если для отсутствующих глифов нужен fallback, меняем только соответствующий fallback после визуальной проверки.
7. Новые интерактивные элементы получают видимый фокус и клавиатурное управление. Для новых анимаций учитываем `prefers-reduced-motion`.
8. Перед первым изменением UI сохраняем визуальные эталоны `/`: первый экран, выбранные Uppermind/Undermind, hero, карточки, терминал и мобильное меню. В сравнении учитываем фазу анимаций; случайный кадр canvas не служит доказательством регрессии.
9. Каждый этап с UI завершаем сравнением лендинга с эталоном и просмотром workspace. Первые размеры проверки: desktop 1440×900 и 1280×800, узкий экран 390×844. На desktop три области видны одновременно; на узком экране остаются три именованных представления с доступным переключением.

Критерий: новый экран воспринимается частью того же WUJI; изменения лендинга ограничены согласованной точкой входа и позднее — актуализацией продуктовых текстов.

## 3. Границы первой версии

Первый законченный цикл:

1. Загрузить недельное расписание по описанному шаблону и проверить распознанные данные.
2. Указать отсутствие сотрудника, закреплённые назначения и обязательные ограничения.
3. Получить различные допустимые варианты, когда они существуют.
4. Сравнить перестановки, затронутых людей, часы, покрытие и стоимость при известных ставках.
5. Открыть исходную строку, правило и проверку для выбранного изменения.
6. Утвердить точную версию результата и скачать файл.

Одна площадка, одна неделя, один явно заданный часовой пояс и одна валюта на проект. Начинаем с синтетического примера порядка 10–20 сотрудников; это размер демонстрации, а не заявленная граница производительности.

Обязательные правила первого движка: подходящая роль, известная доступность, отсутствие пересечений, сохранение закреплённых назначений, заданные пределы часов и заданное покрытие. Все поддержанные правила описываем явно. Если выполнение невозможно, обязательные условия автоматически не ослабляем.

Первый шаблон импорта — CSV с описанной структурой. XLSX с фиксированными листами добавляем после проверки того же цикла на CSV. Произвольные таблицы, PDF и скриншоты остаются за пределами первой версии.

## 4. Этапы и результаты

### Этап 0. Зафиксировать визуальный эталон и предметный пример

Результат:

- снимки и краткий каталог существующего дизайна;
- шаблон входных данных и описание поддержанных правил;
- синтетический пример с исходником, отсутствием, корректными вариантами и вручную проверенными ожидаемыми метриками;
- дополнительные случаи: неизвестная ставка, неизвестная доступность, несовместимые условия и отсутствие необходимости в изменениях.

У данных есть устойчивые `employeeId`, `shiftId`, `ruleId` и ссылки на источник. Рабочие версии источника и условий имеют отдельные ID. Денежные суммы сопровождаются валютой, длительности — единицами, время — часовым поясом. Время внутри расчёта представляем в целых минутах, денежные вычисления выполняем без двоичного float с явным правилом округления.

Готово, когда данные достаточны для демонстрации и каждый показанный итог можно проверить вручную. Реальный обезличенный пример нужен для подтверждения контракта пилота; его отсутствие не блокирует работу над синтетическим UI.

### Этап 1. Рабочее пространство на демонстрационных данных

Результат — маршрут `/workspace` в текущем дизайне.

| Слева: исходник | В центре: задача и условия | Справа: сценарий |
| --- | --- | --- |
| Файл, версия, таблица расписания | Поле задачи и редактируемые структурированные условия | Выбранный вариант и обновлённое расписание |
| Сотрудники, назначения, неизвестные значения | Обязательные правила, предпочтения, допущения | Список изменений, метрики, статус проверки |
| Подсветка исходной строки | Источник и объяснение выбранного изменения | Переключение и сравнение вариантов |

Начальная ширина областей — 35/30/35; разделители изменяются мышью и клавиатурой, панели прокручиваются независимо. Дополнительные сведения раскрываются внутри этих областей.

Взаимодействия: загрузить пример, выбрать отсутствие в форме, переключить заранее подготовленный вариант, нажать на изменение, увидеть связанную строку и её основания. Демонстрация обрабатывает только описанные примеры и не изображает понимание произвольного запроса.

Поставщик данных отделён от компонентов интерфейсом `WorkspaceClient`: сначала demo-реализация, позднее HTTP. Предметные сущности не копируем вручную по компонентам. Статусы и метрики демонстрации явно помечены как демонстрационные; кнопки реального ИИ, утверждения и экспорта активируются только после реализации соответствующих операций.

Готово, когда весь демонстрационный путь проходит в браузере, выбор связан по ID во всех трёх областях, состояния неизвестности видны, а визуальные проверки подтверждают сохранение дизайна. Первая итерация реализации заканчивается здесь.

### Этап 2. Настоящие данные, версии и сохранение

Результат:

- Python/FastAPI-приложение в `backend/`, PostgreSQL и миграции;
- проекты, оригиналы файлов, неизменяемые SourceVersion, TaskSpec и сохранение версий;
- CSV-импорт с проверкой столбцов, типов, ID, ссылок, дат и единиц; затем XLSX по фиксированному шаблону;
- предварительный просмотр, ошибки по строкам и подтверждение импорта до создания рабочей версии;
- сохранение оригинала, hash и адреса происхождения каждого существенного значения;
- экспорт нормализованного расписания и проверка повторным импортом;
- HTTP-реализация WorkspaceClient вместо demo-данных.

Ошибочные и неизвестные значения не исправляются молча. Неоднозначное локальное время требует уточнения; переход через полночь и смену UTC-смещения имеет заданную семантику. Ставки отсутствуют — денежная оценка недоступна, часы продолжают считаться.

Backend-схемы/OpenAPI становятся источником API-контракта, из которого получаем типы клиента. Оригиналы локально храним в каталоге с метаданными в БД. Конфигурация фронтенда и сервера разделена; секретов во фронтенде нет.

Готово, когда проект восстанавливается после перезапуска, версия исходника неизменна, все записи учтены, а импорт → экспорт → импорт сохраняет существенные значения и ID. До аутентификации этот контур используется локально с синтетическими данными.

### Этап 3. Расчёт и независимая проверка

Результат:

- OR-Tools CP-SAT строит расписания по подтверждённым условиям;
- отдельный валидатор заново проверяет назначения и обязательные правила;
- расчёт разницы, часов, покрытия и доступной денежной стоимости;
- варианты с разными приоритетами: минимум перестановок; минимум стоимости при достаточных ставках; дополнительный компромисс только при отличающемся результате;
- Evidence связывает изменение и метрику с исходником, правилом и выполненной проверкой;
- Run сохраняет версии источника, условий и движка, параметры поиска и журнал наблюдаемых событий.

Расчёт выполняется отдельным worker-процессом из того же backend-кода. Запуск сохраняется до выполнения; API возвращает ID задания, UI читает его состояние. Нужны ограничение времени, отмена, повтор и обнаружение зависших запусков. Для первой реализации достаточно опроса состояния; выбор очереди не требует выделять микросервисы.

Раздельно храним состояние выполнения Run, статус поиска и результат валидации. `FEASIBLE` не объявляется доказанным оптимумом, `UNKNOWN` — доказанной невозможностью. Недопустимый результат не доступен для утверждения. Частичное принятие становится новыми закреплениями с повторным расчётом.

Готово, когда контрольные задачи воспроизводятся, обязательные ограничения проверены независимо от solver, невозможный случай не подменяется ослабленными правилами, а суммы и изменения совпадают с данными. После этого этапа уточняем оставшийся объём по фактическим данным.

### Этап 4. ИИ в центральной области

Результат:

- один серверный адаптер провайдера; доступная модель и состояние подключения показаны явно;
- запрос преобразуется в черновик TaskSpec с подтверждением существенных условий;
- неизвестные сотрудники, неоднозначность, отсутствующие факты и неподдержанные правила требуют уточнения;
- модель вызывает только разрешённые операции, а назначения рассчитывает прежний движок;
- объяснения опираются на Evidence и фактические метрики;
- лимиты, отмена, ошибки, доступный usage и стоимость анализа при известном тарифе.

Неизвестная доступность не превращается в разрешение. Инструкции внутри импортированного файла остаются данными. Смена модели создаёт следующий запуск; сохранённые результаты сохраняют прежние метаданные. Затраты на анализ, фонд оплаты и цена перестановок показаны отдельно.

Готово, когда контрольные формулировки дают ожидаемые условия или явное уточнение; объяснение не расходится с результатом, ошибка провайдера не теряет проект, неподтверждённые существенные факты не попадают в утверждаемый сценарий. Второй адаптер добавляем после работающего цикла первого.

### Этап 5. Надёжный цикл и подготовка пилота

Статус: локальный законченный цикл реализован; многопользовательская аутентификация и готовность бизнес-пилота остаются открытыми.

Результат:

- утверждение фиксирует точные версии источника, условий и сценария;
- изменившийся источник вызывает конфликт; поздний ответ старого запуска не заменяет актуальный;
- ручное редактирование создаёт новую версию и снимает статус проверки до её повторного выполнения;
- повторные запросы утверждения и экспорта не создают противоречивых записей;
- аутентификация, изоляция проектов, файлов и запусков до работы нескольких пользователей с реальными данными;
- понятное восстановление после отмены, ошибки или перезапуска worker;
- воспроизводимый локальный запуск, CI и документация ограничений.

Утверждение, экспорт и внешнее применение имеют разные статусы. В первой версии конечное действие — выдача файла; запись в рабочую систему реализуется отдельным последующим этапом.

Готово к пилоту, когда проверены конфликты, отмена, повтор, ручная правка, повторное чтение экспорта и невозможность доступа к чужому проекту. Пилот подтверждает удобство на нескольких повторяющихся реальных задачах и проверяет готовность оплатить следующий эпизод.

## 5. Первый набор изменений: конкретный порядок

Этот набор реализован в первой итерации; ниже сохранено исходное разбиение задач для сопоставления с результатом.

1. **Визуальный эталон и данные.** Сохранить снимки существующих состояний; описать входные сущности, подготовить demo-fixtures и вручную проверенные ожидаемые результаты.
2. **Каркас workspace.** Добавить `src/pages/Workspace.tsx`, маршрут в `src/App.tsx`, три области и разделители. Рабочие стили ограничить новой страницей. Проверить прямое открытие URL, фокус и отсутствие горизонтальной прокрутки всей страницы.
3. **Предметный интерфейс.** Добавить компоненты источника, задачи и сценария, таблицу расписания, список изменений, метрики и статусы. Подключить demo-реализацию WorkspaceClient.
4. **Сквозное взаимодействие.** Реализовать выбор варианта и связанное выделение по ID; раскрытие источника, условия и объяснения в центре; состояния неизвестных ставок и невозможного примера.
5. **Вход и приёмка.** Добавить вход с `/` в существующем стиле, пройти demo-сценарий, проверить desktop и узкий экран, сравнить лендинг с эталоном и выполнить `npm run build`.

Предлагаемое размещение новых файлов:

```text

  model/                  типы, выбор объекта/варианта, состояния интерфейса
```

Минимальные сущности интерфейса: SourceVersion, TaskSpec, Run, Scenario, ChangeSet, Evidence. Approval и Export подключаются вместе с реальными операциями, а не с демонстрационной сменой надписи.

## 6. Проверки по мере появления поведения

| Что проверяем | Как принимаем |
| --- | --- |
| Сохранение дизайна | Визуальные эталоны лендинга, просмотр workspace и состояний на заданных размерах; проверка фокуса и читаемости |
| Связь трёх областей | Браузерный сценарий: выбрать вариант → изменение → исходную строку и основание |
| Импорт и экспорт | Контроль количества записей, типов, ID, происхождения; повреждённые файлы; повторное чтение экспорта |
| Расписание | Валидный исходник, отсутствие, закрепления, роли, пересечения, пределы часов, покрытие, неизвестная доступность |
| Метрики | Независимые ожидаемые суммы, длительности, округления, валюта; отсутствующие ставки и смешанные валюты |
| Статусы | Решение найдено, оптимальность не доказана, невозможность доказана, поиск остановлен, неверная модель, нарушение при валидации |
| Версии и задания | Поздний ответ, новый исходник, ручная правка, отмена, повтор, перезапуск worker |
| ИИ | Контрольные запросы с ожидаемым TaskSpec, неоднозначность, неподдержанные условия, текстовые инструкции из файла |
| Доступ | Попытки прочитать или изменить чужой проект, запуск, оригинал и экспорт |

Проверки добавляются вместе с функцией. Сейчас проходят 152 backend-теста с настоящим PostgreSQL и 39 тестов TypeScript/HTTP-клиента, проверка API-типов и production-сборка. Связь трёх областей, импорт, версии, расчёт, отмена, закрепления, текстовые черновики, ручная правка/повторная проверка, утверждение, скачивание и узкий экран проверены в браузере. CSV/XLSX повторно прочитаны без потери назначений и поддержанных условий. OpenAI SDK проверен через MockTransport без сети. Живое качество разбора, Linux CI и общий доступ ещё не приняты.

## 7. Вопросы для реального пилота и последующие решения

Для подтверждения входного контракта понадобятся обезличенное расписание, источник доступности, обязательные правила команды, формат выдачи и реальный эпизод отсутствия. До их получения используем явные синтетические условия и не объявляем контракт проверенным на бизнесе.

Для первой интеграции выбраны OpenAI, gpt-5.4-mini-2026-03-17 и бюджет по умолчанию 0,05 USD на разбор; успешный живой цикл ещё предстоит подтвердить. Очередь уже хранится в PostgreSQL и исполняется отдельным worker. Площадку размещения backend и способ аутентификации выбираем при подготовке пилота. Лицензия и коммерческая граница решаются владельцем до открытого релиза.

Сроки не объявляем до проверки предметного контракта и первой интеграции движка. Порядок обязательных результатов: **интерактивный workspace → собственные данные и версии → проверенный расчёт → ИИ → законченный цикл и пилот**.

## 8. Основания отдельных технических решений

- [OR-Tools: статусы CP-SAT и целочисленная модель](https://developers.google.com/optimization/cp/cp_solver). Используем как основание для раздельных статусов поиска и целочисленных величин в solver; корректность WUJI подтверждается собственным валидатором и примерами.
- [FastAPI: ограничения BackgroundTasks для тяжёлых вычислений](https://fastapi.tiangolo.com/tutorial/background-tasks/#caveat). Отдельный worker — выбранное для WUJI решение с учётом ограничения времени, отмены и восстановления запусков; конкретную очередь этот источник не предписывает.
